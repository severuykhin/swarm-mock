# План реализации фазы 1 (HTTP API-заглушка)

## 1. Цели и ограничения
- Поднять HTTP-сервис, соответствующий спецификации из [docs/swarm-spec/spec.md](docs/swarm-spec/spec.md).
- Реализовать обработчики всех путей (`Get`, `GetK1`, `Set`, `Delete`) с возвратом статуса 200 и тестовыми ответами без бизнес-логики.
- Подготовить структуру проекта и каркас зависимостей так, чтобы на фазе 2 осталось реализовать только прикладной код.

## 2. Архитектурный каркас
- Создать отдельный Go-модуль в каталоге `main` с базовыми зависимостями: стандартная библиотека, выбранный HTTP-роутер (например, github.com/go-chi/chi v5).
- Выделить слои приложения:
  - слой транспорта (инициализация HTTP-сервера, регистрация маршрутов, middleware);
  - слой обработчиков (функции, маппящие HTTP-запросы на вызовы сервисного слоя);
  - сервисный слой (интерфейс и простая заглушка, возвращающая статические данные/успех);
  - инфраструктурные утилиты (конфигурация, логирование, graceful shutdown).
- Подготовить заготовку интерфейса для будущего KV-хранилища, но внутри заглушки возвращать stub-значения.

## 3. Структура каталогов
- `main/cmd/server` — точка входа сервиса, чтение конфигурации, запуск HTTP.
- `main/internal/http` — сборка роутера, middleware, регистрация обработчиков.
- `main/internal/handler` — конкретные обработчики запросов.
- `main/internal/service` — интерфейсы и простая заглушка бизнес-логики.
- `main/internal/config` — чтение переменных окружения и базовых настроек (порт, таймауты).
- `main/internal/logger` — фабрика логгера (например, zap или стандартный log).

## 4. HTTP-маршруты и поведение заглушки
- GET `/swarm/{k1Prefix}/{k1Suffix}/{k2}/` и `/swarm/{k1Prefix}/{k1Suffix}/{k2}/{k3}/` → возвращать 200 с пустым телом или фиксированным бинарным blob.
- GET `/swarm/{k1Prefix}/{k1Suffix}/` с query `t=...` → 200 с пустым телом или фиксированным бинарным blob.
- PUT `/swarm/{k1Prefix}/{k1Suffix}/{k2}/{k3}/` (или без `{k3}`) → 200 без чтения тела либо с имитацией валидации.
- DELETE `/swarm/{k1Prefix}/{k1Suffix}/{k2}/{k3}/` (или без `{k3}`) → 200 с JSON `{ "deleted": true }` либо пустым телом.
- TODO-комментарии в коде, указывающие, где на фазе 2 появится реальная логика обработки тела, обращения к хранилищу, возврата кодов `404` и т.д.

## 5. Инфраструктурные элементы
- Добавить поддержку graceful shutdown (контекст, os.Signal) для корректной остановки сервера.
- Реализовать базовое логирование запросов и ошибок (middleware либо обертка над обработчиками).
- Предусмотреть конфигурацию порта (значение по умолчанию, переопределение через переменную окружения `SWARM_STUB_HTTP_ADDR`).

## 6. Валидация запуска
- Написать README-инструкцию в каталоге `main` с описанием запуска: `go run ./cmd/server`.
- При необходимости добавить минимальные unit-тесты для проверки сборки маршрутов (использовать httptest для smoke-проверок статусов 200).
- Проверить `go fmt`, `go vet`, `golangci-lint` (если доступен) для подготовленных файлов.
